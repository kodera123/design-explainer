# 設計の説明ページを作る

読み手が5分で読んで、設計に大きな抜けがないかを判断できるページを作る。仕様書ではないので、網羅しない。

**作る前に目的と構成を合わせる。1つの節は図1枚と1〜3文。同じ例を最後まで使う。別のエージェントに読ませて確かめる。**

実装者向けの仕様書、ADR、PR 本文には使わない。「設計書を作って」と頼まれたときは、作るのがレビュー用の説明ページであることを、構成の案で伝える。

## 手順

1. **目的を1文で確かめる。** 誰が、読んで何を判断するのか。何分で読むのか（既定は5分）。依頼から読み取れたら、構成の案の1番目に書いて確かめる。読み手か、判断することが分からないときだけ、先に聞く。
2. **材料を疑う。** 依頼のメモ、元の設計ページ、コードを読み直して事実を確かめる。構成に効く事実（今のテーブルの形、処理の入口）は構成の案の前に読む。残りは、図を作る前までに読む。確かめられないものは「未確認」と書く。
3. **構成の案を出して止まる。了承をもらうまで、図も本文も作らない。** 急ぎでも同じにする。構成の案は数分で出せるが、作り直しには数時間かかる。止まらずに進めるのは、ユーザーが「確認は要らない」と言葉で指定したときと、返事をする相手がいない実行のときだけ。そのときも案は書き、報告の先頭に載せる。聞けなかった点は、仮に決めた内容を未決定としてページに載せる。置き場所が分からなければ、Notion には載せずにファイルで渡す。案の書き方は `references/outline-example.md`。すでにあるページを直すときも同じで、今のページを材料として読み、残す節、削る節、作り直す図を案に書く。
4. **図を作る。** `scripts/figkit.py` を使う。`scripts/example_figures.py` が動く見本で、型の節ごとの図が7種類ある。図のスクリプトと出力は、ユーザーのリポジトリの外の作業用フォルダ（一時フォルダなど）に置き、見本の先頭と同じ書き方で figkit を読み込む。保存のときに「はみ出しそう」と出た行は、短くするか `wrap` で分ける。出なくても、PNG を1枚ずつ開いて見る。
5. **本文を書いて、字数を数える。** 文章を整えるスキルや文体の決まりが入っていれば、それに従う。なければ、1文に1つのことを書き、作業中に付けた呼び名や略語を使わない。
6. **別のエージェントに確かめさせる。** `references/comprehension-check.md` の頼み方を使う。
7. **Notion に載せて、画面で見る。** `references/notion-publish.md`。Notion やブラウザのツールが無い環境では、本文の markdown と図の PNG をファイルで渡し、載せた画面を見ていないことを報告に書く。
8. **報告する。** URL、字数（毎分500字と400字での分数、目安を超えた分）、確かめた結果、未確認の点、読み手役から出た設計への疑問。

## ページの型

| 節 | 読み手が確かめられること | 図 |
|---|---|---|
| 何を作るか | 今は何ができなくて、何を足すのか | なし（3〜4文） |
| 今どう残っているか | 今のテーブルに何が残り、何が残らないか | 代表的な例3つ × 今のレコード |
| 1回の処理ですること | どのテーブルを見て、どう処理するか | 手順の流れ。手順ごとに見るテーブル |
| 残るレコード | カラムに過不足がないか | 行の例と、その下にカラムと使い道の表。持たせていないものと理由は箇条書き |
| 例で結果を確かめる | 想定している数字と合うか | 同じ3つの例の結果と合計 |
| 変更が起きたとき | 例外をどうカバーしているか | 起きたこと・レコード・結果（3〜4件） |
| 下流での動き | 集計や表示にどうつながるか | テーブルから画面までの流れ |
| 見てほしい点 | 決めたことが何を引き起こすか | Notion の表（決めたこと・その結果） |
| 参考 | — | `## 参考` の見出しの下に、細かい決まり、カラムの型、算出の詳細を折りたたみで置く |

題材に合わせて節を足し引きする。「今 → 処理 → 残るもの → 結果 → 例外 → 下流」の順は保つ。

- 処理が1つのバッチでなく、複数の操作（付与・利用・取り消しなど）のときは、「1回の処理ですること」を「操作ごとに、読むテーブルと書くテーブル」にする。
- 1回きりの移行は、節を立てずに、例の1つと「見てほしい点」で見せる。
- 新しいテーブルを足す設計で、今は何も残っていない例があるときは、「今は残らない」ことを空の行で見せる。

## 図と文の決まり

- 1つの節は、図1枚（多くて2枚）と1〜3文。図に書いたことを文で繰り返さない。
- 例は3つ。名前を付けて（A さん・B さん・C さん、web-1・db-1・batch-1 など）、例を出す図では最後まで同じ例、同じ日付、同じ金額を使う。形の違う例を並べて比べる。1つの例の中に出来事が2〜3個並ぶのはよい。避けるのは、例が1つだけで、長い時系列を追わせること。
- 色は1枚の図に1つの意味だけで使い、凡例に1行で書く。行の例の図では、いちばんふつうの行を基準として1行目に置き、基準と違う所に付ける。ID や対象の月のように行ごとに違って当然のカラムは、色を比べる列にせず、行の見出し（「db-1 の 12月」など）で表す。カラムそのものは、行の例の下に置く「カラムと使い道」の表に載せる。例を並べた結果の図では「前の列から変わった所」、操作の図では「今回足す処理」、例外の図では「まだ決まっていない所」のように、その図で見てほしい1種類に付ける。見てほしい所が無い図には付けない。
- テーブル名とカラム名は図に入れる。読み手は、どのテーブルのどのカラムがどう使われるかを見る。
- カラムの一覧や行の例は、Notion の素の表にしない。素の表は、4行ほどの短い表だけに使う。
- 5分は、図の中の文字を含めて約2,500字（毎分500字）。参考の節は数えない。図は1枚 130〜450字（多くは 200〜300字）で、6枚なら 1,500〜1,800字になり、本文に使えるのは約700字。構成の案の時点で「図の枚数 × 300 ＋ 本文 700」で見積もり、2,500字を超えるなら図を減らすか、節を参考へ回す。
- 字数は `python3 scripts/figkit.py count 本文.md 図.html …` で数える。本文の `[図 …]` の行と、「参考」だけの見出し（`## 参考`）から後ろは合計に入らない。2,500字を1割を超えて上回ったら、削るか参考へ移す。1割以内なら、超えた字数を報告に書く。毎分400字での分数は、ゆっくり読む人の目安として報告に並べる。
- 未確認、未決定、設計の欠点（持たせていないもの）は、隠さず本文に書く。
- 材料を読んで自分が気づいた設計のあいまいな点は、図が描けなくなるものだけを構成の案と一緒に聞く。残りは「未決定としてページに載せる候補」として見せ、ユーザーに削ってもらう。

## よくある失敗

| しがちなこと | 代わりにすること |
|---|---|
| 急ぎと言われ、構成を見せながら作り始める | 構成の案だけを出して止まる |
| 置き場所や細部への答えだけを、構成の了承として扱う | 進める言葉（作って、よろしく）がなければ、構成を1文で確かめる。読み方は `references/outline-example.md` |
| メモの全項目を入れる。ER 図と全カラムの定義表を載せる | 判断に要るものだけにして、残りは参考へ |
| 1つの例を最初から最後まで追う（1人の入会から解約まで、など） | 代表的な3つの例を並べる |
| Mermaid と素の表で済ませる | figkit の図にする |
| 読み手役に「分からない言葉を挙げて」とだけ頼む | 1回だけ読ませ、見返さずに問いに答えさせる |
| 取得し直した markdown を読んで、表示を確認済みとする | ブラウザで画面を見る |
| 直した後を確かめずに「確認済み」と書く | もう一度読ませるか、「直した後は未確認」と書く |
